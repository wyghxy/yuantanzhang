# 升级与数据保留

不同版本使用的存储格式不同，升级代码不会自动完成数据迁移，也不会代替备份。

| 版本 | 数据位置 | 保留入口 |
| --- | --- | --- |
| 0.3.0 | 本地 SQLite 文件与上传目录 | 当前版本 |
| 0.2.0 | PostgreSQL、上传目录及原运行配置；任务使用 Redis/BullMQ | [`v0.2.0` 标签](https://github.com/wyghxy/yuantanzhang/tree/v0.2.0) |
| 旧浏览器版 | 原浏览器来源下的 IndexedDB | [`legacy-browser-v0.1.0` 标签](https://github.com/wyghxy/yuantanzhang/tree/legacy-browser-v0.1.0) 或[固定提交](https://github.com/wyghxy/yuantanzhang/tree/40f47f3b0a8681d122658d4d7e5e4d34b477fd87) |

## 从 0.2.0 PostgreSQL 版本升级

先保留旧 PostgreSQL 数据库的有效备份、上传媒体目录、个人环境配置和 `v0.2.0` 源码。备份使用原数据库适用的导出或备份方式，不通过正在运行时复制数据库目录来代替。

在独立目录安装 0.3.0，使用新的 SQLite 数据文件与上传目录，按 [安装说明](installation.md) 初始化。不要让新版本覆盖旧 `.env`、媒体目录或数据库，也不要让两个版本共用可写的数据文件。

**目前没有 PostgreSQL 到 SQLite 的自动迁移器。** PostgreSQL 的表目录、数据库备份或 SQL 文件不能直接复制为 SQLite 文件使用；简单改动 `DATABASE_URL` 也不会转换原有稿件、版本和关联。

需要继续使用原有完整资料时，可以保留旧版本运行环境，在原版本中读取和导出所需内容。新版本现有素材导入可收录正文、本地文本和媒体；这不等于迁移全部历史 ID、版本、笔记或关联。对完整迁移有需求时，应另行实现并验证迁移工具后再切换。

需要回到 0.2.0 时，使用对应标签的源码及其原有数据库、媒体和配置。旧版本不能直接读取 0.3.0 的 SQLite；回退代码也不自动恢复数据。保留新版本运行后新增的资料，再处理任何数据恢复或替换。

## 从旧浏览器版升级

在原来的浏览器、域名和端口打开旧工作台 `/desk/`，导出 JSON 备份，并导出需要继续创作的 Markdown 或正文。确认导出文件能够读取后，再安装新版本。不要为了升级清空浏览器站点数据。

旧代码、许可和导出工具保留在上方的旧版入口，便于继续读取原资料。浏览器的完整 JSON 备份单独保存；目前没有把其中全部笔记、ID 和关联自动转换为 SQLite 的迁移器，不能把 JSON 直接覆盖到新数据库文件中。

0.3.0 默认网站端口为 3310。更换端口或启动新版本不会替你删除旧浏览器的数据，但也不会自动读取或备份它们。

## 0.3.0 本地数据备份

停止应用与独立 Worker 后，备份 SQLite 主文件、仍存在的同名 `-wal` / `-shm` 文件、上传目录和个人环境配置。将这些文件作为同一份恢复集合保留，不在应用写入过程中只复制主文件。

恢复前保护当前新增资料，并使用与备份兼容的代码和迁移版本。代码仓库、截图和演示种子都不能代替自己的业务数据备份。
